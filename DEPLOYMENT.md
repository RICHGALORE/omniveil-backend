# Omni Veil Backend Deployment

The production API is designed for Render with Render PostgreSQL. `render.yaml` is the canonical infrastructure contract for the service, database, persistent disk, health check, and non-secret environment settings.

## Render Blueprint contract

The checked-in `render.yaml` declares:

- Docker web service `omniveil-backend` on paid `0.5c-512mb` compute;
- `autoDeployTrigger: checksPass` so GitHub CI must pass before automatic deployment;
- platform health check at `/health`;
- a 10 GB persistent disk mounted at `/app/uploads`;
- paid `omniveil-db` Postgres on `0.1c-256mb` compute;
- `DATABASE_URL` linked from that database;
- `ENVIRONMENT=production`, `UPLOAD_DIR=/app/uploads`, and production demo seeding disabled;
- tenant-scoped rate-limit defaults for Upload, OmniSpectra scan, external detector refresh, and C2PA;
- `OV_SIGNING_SECRET` and `ADMIN_API_KEY` generated by Render as persistent random 256-bit values when they do not already exist;
- externally supplied secrets declared with `sync: false` so their values are never committed.

Render preserves existing resources with matching names when a Blueprint is synced. Treat a Blueprint sync as an infrastructure change: review the Render diff before applying it. Persistent disks require a paid Render web service.

## Required production secrets

Render can generate the generic application secrets automatically. These remaining values must be stored in Render's secret/environment configuration and must never be committed:

- `OV_SIGNING_PRIVATE_KEY_B64` — production Ed25519 Trust Authority private key
- `OV_SIGNING_PUBLIC_KEY_B64` — matching production Ed25519 public key
- `OV_SIGNING_KEY_ID` — stable production key identifier, for example `OV-ROOT-PROD-001`
- `ALLOWED_ORIGINS` — canonical production Vercel origin(s), comma-separated, without trailing slashes
- `SIGHTENGINE_USER` / `SIGHTENGINE_SECRET` when Sightengine forensic detection is enabled
- `HIVE_MEDIA_API_KEY` for Hive image/video synthetic-media detection
- `HIVE_AUDIO_API_KEY` for Hive general audio synthetic-media detection
- `HIVE_MUSIC_API_KEY` for Hive generated-music / AI-music-cover evidence

`HIVE_API_KEY` remains supported only as a legacy visual-media fallback. Production should use the explicit Hive project/model keys so image/video, general audio, and music evidence cannot be silently attributed to the wrong model family.

For a new Blueprint, Render generates `OV_SIGNING_SECRET` and `ADMIN_API_KEY` once and preserves them across re-syncs. If those variables already exist on an existing service, their current values are preserved rather than rotated automatically.

If the existing Render service is already managed by a Blueprint, adding a new `sync: false` variable does not populate its value automatically. Set missing external secret values manually in Render before expecting the related production proof to pass.

The service validates that the configured Ed25519 public key belongs to the configured private key and refuses to issue certificates in production if signing configuration is missing, invalid, or mismatched. It never falls back to the local development root when `ENVIRONMENT=production`.

If production demo seeding is deliberately enabled, set `DEMO_API_KEY` explicitly. The service will not generate or log a production demo credential.

## Container contract

Build from the repository `Dockerfile`. The container:

- runs Python 3.11 as an unprivileged user;
- installs ExifTool for metadata extraction;
- uses `/app` as its working directory;
- pins `UPLOAD_DIR=/app/uploads` so application and Render disk paths agree;
- listens on Render's `PORT` value;
- exposes `/health` for process liveness;
- exposes `/ready` for dependency readiness.

`/health` deliberately stays lightweight so infrastructure can tell whether the API process is alive even during a database/configuration incident. `/ready` is the stricter gate and checks database connectivity, writable persistent upload storage, and production Trust Authority signing configuration. It returns HTTP `503` when any required dependency is unavailable and exposes only public-safe booleans, never credentials or secret details.

External forensic providers are optional dependencies and therefore do not control `/ready`. Their live state is proven separately with `scripts/production_forensic_proof.py` so an outage at one vendor does not make the entire Trust OS unavailable.

## Persistent storage

Uploaded originals, watermarked files, certificates, and manifests are written under `/app/uploads`. The Render disk must be mounted at that exact path before accepting production uploads. Only files under the disk mount survive deploys and restarts.

The storage helper also understands legacy database paths such as `uploads/originals/...`, so existing records remain resolvable after the persistent root becomes explicit.

## Release check

After deployment, verify liveness first:

```bash
curl https://omniveil-backend.onrender.com/health
```

Expected response:

```json
{"status":"ok","version":"0.1.0","env":"production"}
```

Then verify the service is actually ready to accept Trust OS work:

```bash
curl -i https://omniveil-backend.onrender.com/ready
```

Expected production response after Postgres, persistent storage, and signing secrets are configured:

```json
{
  "status": "ready",
  "ready": true,
  "environment": "production",
  "checks": {
    "database": true,
    "storage": true,
    "trust_signing": true
  }
}
```

Before accepting uploads, issue one controlled certificate and verify that its `public_key_id` is the configured production key ID, never `OV-ROOT-DEV-001`.

## Executable production proof

Use `scripts/production_proof.py` to replace the controlled-certificate manual check with a full Trust OS proof. The runner validates readiness, fresh ingest, watermark storage, HumanProof continuity and asset binding, Ed25519 certificate identity, public Verify, Registry, Evidence Graph, and Fact Integrity.

```bash
export OV_API_KEY='YOUR_TENANT_API_KEY'
export OV_EXPECTED_SIGNING_KEY_ID='OV-ROOT-PROD-001'
python scripts/production_proof.py --report production-proof-create.json
```

Then restart or deploy the Render service and recheck the same asset to prove database + persistent disk survival:

```bash
python scripts/production_proof.py \
  --recheck-omni-id 'OV-...' \
  --expected-cert-id '...' \
  --report production-proof-recheck.json
```

## Executable forensic-provider proof

After the core production proof is green, use `scripts/production_forensic_proof.py` to prove the external detector layer independently. By default it requires both Sightengine and Hive, confirms provider probabilities remain separate, verifies detector refresh did not rewrite registration or Trust Score facts, and confirms provider observations appear in Evidence Graph.

```bash
export OV_API_KEY='YOUR_TENANT_API_KEY'
export OV_EXPECTED_DETECTOR_PROVIDERS='sightengine,hive'
python scripts/production_forensic_proof.py \
  --omni-id 'OV-...' \
  --report production-forensic-proof-create.json
```

For a Heavy Handed Productions audio flagship, configure Sightengine plus at least the appropriate Hive audio/music project key before running this proof. For an image/video proof asset, configure `HIVE_MEDIA_API_KEY`.

After a Render restart/deploy, prove the forensic observations themselves survived without spending another vendor call:

```bash
python scripts/production_forensic_proof.py \
  --omni-id 'OV-...' \
  --no-refresh \
  --report production-forensic-proof-recheck.json
```

A passing `--no-refresh` run proves the provider-specific rows remained in Postgres and still surface in both OmniSpectra and Evidence Graph.

See `docs/PRODUCTION_PROOF_RUNBOOK.md` for the complete proof conditions, failure semantics, and security boundary.
